# 划词评论与 Agent 对话

日期：2026-10-28。状态：用户已批准；本地实现和独立验证完成，待用户体验验收。验证记录：`docs/validation-2026-10-28-content-annotations.md`。

## 用户已明确的目标

正常阅读网页时，选中文字即可发表评论。Agent 自动处理这条评论，界面显示回复中的状态和回复结果，交互参考飞书评论。

用户已明确选择：**按评论内容判断，问题就回答，修改要求就执行并回复结果。** 不要求用户每次先选择“问答”或“修改”。

批准时补充的边界：这是独立的“页面内容批注”，不需要打开评论模式；入口、记录、对话与原先的评论错开。以下“评论”在新能力上下文中均指内容批注。新数据保存到 `annotations.json`，原 `comments.json`、评论列表和批次范围不变。

## 现状与依据

- `runtime/review.js` 已支持“评论模式 → 文字 → 拖选 → 保存”，但正常阅读时的选区没有评论入口。
- 当前“交给 Codex”冻结所有页面的全部待处理评论；不能直接作为单条评论自动回复的入口。
- `runtime/codex_session.py` 已持久化流式消息、完成结果和失败状态，可沿用现有本机通道。
- 当前任务 API 只服务于 current job，需要扩展为按评论查找和继续对话。
- 当前文字锚点只有引用文本和容器相对矩形，需要补充可恢复的文字范围。
- [官方评论说明](https://www.larksuite.com/hc/zh-CN/articles/680083197034-%E5%9C%A8%E4%BA%91%E6%96%87%E6%A1%A3%E4%B8%AD%E4%BD%BF%E7%94%A8%E8%AF%84%E8%AE%BA%E5%8A%9F%E8%83%BD)描述了选中文字、评论入口、右侧输入和评论内回复的流程。此处仅作为公开交互依据，尚未完成登录后的飞书实际文档操作验证，不声称像素复刻。

## 方案比较与建议

1. **推荐：每条划词评论独立对话，沿用本机 Agent 通道。** 引用、用户消息、处理状态和 Agent 回复集中在同一评论里，支持继续追问。需要增加单条任务归属、队列与历史读取。
2. 将单条评论接到现有批处理任务面板。改动较小，但会混淆评论上下文，并可能带入无关待处理评论，不符合此次体验。
3. 新接模型 API 或另起 Agent 启动器。需要新的凭据和运行机制，超出本轮范围。

用户已批准独立对话方案，并要求使用独立的页面内容批注入口与记录。

## 用户流程

1. **选中文字**：无需先进入评论模式。鼠标、触摸或键盘产生非空正文选区后，在选区附近出现轻量“评论”按钮。保留系统复制行为，不干预输入框、可编辑区域和评论组件内部选区。
2. **写评论**：点击后保留原文引用并打开右侧评论卡，输入自动获得焦点。桌面卡片宽约 360px；窄屏使用不超出视口的面板。正文不重排。允许 Esc 取消和 Cmd/Ctrl+Enter 发送，输入法确认不触发提交。
3. **发送**：本机启用 Agent 时，发送区明确提示“Agent 将自动回复或执行修改”。发送一次只处理该评论，评论保存和派发均可安全重试。
4. **看进展**：发送后留在该评论内，显示“等待处理”“Agent 回复中…”或实际修改进度；流式文字属于过程，不作为完成证据。轮询保留输入框、草稿、焦点和用户当前阅读位置。
5. **看结果**：成功保留完整回复。回答问题不改变评审状态；完成源码修改并通过检查后才写入 `changed`，界面显示“待验收”。只由用户解决评论。失败和停止明确显示，并提供重试或继续追问。
6. **继续讨论**：同条评论中的后续消息进入原会话；不同评论彼此隔离。点击正文高亮或评论条目可互相定位。刷新后恢复历史、引用和实际状态，不重新派发已发送消息。

初版回复支持文字；首条评论继续支持现有截图和图片附件。回复中新增图片、多人身份、@提醒和富文本工具不在本轮。

## 文字定位

新文字锚点保留已有字段，追加容器内文本起止位置、原文及前后文。跨行和跨内联元素可恢复真实 Range；使用独立高亮层或浏览器高亮能力，不向业务正文插入包裹节点。

重排或刷新时先验证范围与引用，再使用上下文重新定位。相同文本多处出现且无法唯一匹配时，显示“原文位置已变化”，保留原引用和截图，不将高亮移到猜测位置。旧评论继续使用既有定位回退。

## Agent 与任务边界

- 扩展 `CodexTasks` 和现有 session runner，不添加新启动器。保持 `approval_policy=never`、`sandbox_mode=danger-full-access`，不修改全局配置。
- 单条对话使用独立任务类型和 `commentId`，冻结该评论、引用、页面上下文、证据以及消费者执行配置。后续消息也冻结发送时所需的最新上下文，保留之前的对话历史。
- 提示词要求先按用户内容判断意图：问题直接回答；明确修改要求按消费者源码、构建和检查规则执行；实质不明确时在原评论追问。不会因为评论仍为 `open` 而强制修改。
- 明确修改要求授权任务范围内可逆修改，提交、推送、部署和其他外部动作仍需各自授权。网页正文作为引用内容，不作为越过用户请求的指令。
- 沿用项目级执行锁。不同评论持久化排队，串行处理，避免同时修改同一份源码；界面显示等待状态。同条运行中的追问按已有同会话机制送达；不同评论不做 steer。
- 原有手动普通评论、批次按钮与历史任务继续工作。新 Agent 对话不会被旧的“所有待处理评论”入口再次处理；普通评论仍保持原批处理语义。该排除规则是本方案的明确扩展。

## 数据、幂等与恢复

原评论记录与对话存储分离，新增对话记录放在完整 review data 目录内。评论 ID 关联消息、请求 ID、任务/线程 ID、状态、时间戳和失败信息；不能仅存在浏览器内存或 current.json 中。旧评论整对象写回不能删除对话历史。

发送通过稳定请求 ID 去重。评论保存成功而派发确认丢失时，显示已保存及待确认状态，重试只能确认或补派一次，不能产生第二条评论或第二次执行。队列认领、项目锁和任务状态变更需具有明确的持久化边界。

服务重启后从已持久化状态恢复显示，等待队列可在确认无活动 worker 后继续；已经运行但结果不明的修改任务不自动重放，显示中断并允许用户重试。重试冻结新读到的评论版本，既有修改保留。

已有正文、锚点、截图、附件、创建时间不变。回复消息不更新原评论时间戳；真正修改评论状态时使用刚读取的 `updatedAt` 作为 `expectedUpdate`，冲突不覆盖。更改后的文字重新定位失败不影响原始证据。

导出在保留已有 `comments` 和附件契约的基础上，附带与评论关联的对话及状态快照。离线阅读能显示已携带的回复；没有收到的回复不得虚构。共享端只暴露可公开的回复内容和状态，不暴露本机路径、原始事件日志或可执行任务接口。

## 本轮范围

- 只改 toolkit 的 `runtime/`、独立测试及文档。
- 本机启用桥接的 HTTP 页面支持自动 Agent；共享、离线及显式禁用桥接时仍可划词评论，但只保存评论并说明当前不能自动回复，不排队等待以后自动启动。
- 不升级消费者、不迁移正式数据、不安装发布、不提交推送、不部署。真实消费者任务和评论不用于测试。
- 所有自动化使用合成页面、临时数据、协议替身与隔离的无头 Chrome。本轮正式验证 macOS。

## 验证与交付

新增针对自然选区、跨节点/多行/反向选区、键盘与窄屏、选区保持、引用重定位和旧锚点回退的浏览器检查。

协议与服务检查覆盖单条评论隔离、意图提示上下文、等待/流式/完成/失败/停止、重复提交、响应丢失、服务重启、历史追问、队列和原批任务互斥，以及原证据和时间戳保留。共享/离线/禁用桥接必须证明不会激活 Agent。

完成后运行 README 中的独立 unittest 套件和 `verify.rb`、`verify-attachments.rb`、`verify-shared.rb`，以及新增单条对话浏览器检查。使用合成内容给出可查看的本地交互入口，明确哪些回复是协议替身演示。

只可将这些结果报告为本地实现与协议、浏览器验证。真实模型的意图判断与修改质量、用户视觉接受、发布和生产可用性仍须独立证据。
